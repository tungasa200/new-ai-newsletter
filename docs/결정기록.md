## D-01 언어·런타임
- 상태: 확정 2026-11-11 (사용자 결정 카드 20261111-0100-AN-pm-p1-infra, 추천안 채택)
- 결정: Python 3.12 이상. 의존성은 `anthropic`, `feedparser`, `httpx`(또는 `requests`), HTML 본문 추출 라이브러리 1개, 템플릿 엔진(`jinja2`)으로 한다.
- 근거: 레거시가 Python이고 수집·발송 코드가 이미 동작하는 것이 확인돼 재사용할 수 있다. 공식 Anthropic SDK와 RSS 파서가 성숙했다. GitHub Actions에서 따로 설정하지 않아도 바로 돈다. 배치 작업이라 런타임 성능이 중요하지 않다.
- 대안: ① Node/TypeScript: Vercel·Cloudflare에 잘 맞지만 그 두 호스팅을 추천하지 않으므로 이점이 작다. ② Java: 이 규모에는 빌드·런타임이 무겁고 레거시를 재사용할 수 없다.
- 관련: NFR-07, D-02

## D-02 스케줄·호스팅
- 상태: 확정 2026-11-11 (사용자 결정 카드 20261111-0100-AN-pm-p1-infra, 추천안 채택)
- 결정: GitHub Actions의 비공개 저장소에서 돌린다. cron은 06:30 KST와 07:30 KST 두 번 건다(`30 21 * * *`, `30 22 * * *` UTC). 두 번째 실행은 그날 이미 발송했으면 바로 끝낸다. `workflow_dispatch`로 수동 실행할 수 있게 한다.
- 근거: 비공개 저장소의 Free 포함분은 월 $12 상당(약 2,000분)이고, 이 작업은 월 300분이 안 돼 **추가 비용이 없다**. job 제한은 6시간이라 넉넉하다. 실패 알림·비밀값·로그가 기본으로 들어 있다. 레거시에서 이미 검증된 경로다. 스케줄 지연·드롭 위험[G2]은 cron 2회와 이중 발송 방지로 줄인다.
- 대안: ① Railway Hobby: 월 $5. 실행 시간 제한이 없고 볼륨을 쓸 수 있다. 사용자가 이미 Railway를 쓰고 있다면 관리 지점을 하나로 모을 수 있다(차선). ② Vercel Hobby: 함수 최대 300초, cron 실행 시각이 최대 59분 어긋난다, 비상업 조건이 있다. 비추천. ③ Cloudflare Workers: Free는 CPU 10ms라 부족하다. Paid는 월 $5이고 런타임에 맞춰 다시 써야 하며 SMTP를 쓸 수 없다. 비추천.
- 관련: `docs/호스팅비교.md`, FR-MAIL-01, FR-MAIL-04, FR-OPS-04

## D-03 상태 저장
- 상태: 확정 2026-11-11 (사용자 결정 카드 20261111-0100-AN-pm-p1-infra, 추천안 채택)
- 결정: 상태 저장이 **필요하다**. `state` 가지(main과 분리)에 `sent.json`(최근 90일 발송 항목의 정규화 URL·사건 키·날짜), `runs.json`(최근 실행 결과·소스별 마지막 새 항목 날짜), `knowledge/current.md`(D-09)를 두고, 실행이 끝나면 workflow가 커밋한다. 크기는 수백 KB 이하로 예상한다.
- 근거: 상태가 없으면 ① 릴리스 노트처럼 며칠에 걸쳐 피드에 남아 있는 항목이 매일 다시 실리고 ② 재실행·두 번째 cron에서 이중 발송을 막을 수 없고 ③ 멈춘 피드를 감지할 수 없다. Actions 캐시는 7일간 접근이 없으면 지워져서 쓸 수 없다[G5]. 저장소에 커밋하면 외부 서비스가 필요 없고, 사람이 이력을 보고 고칠 수 있다.
- 대안: ① 외부 DB(Cloudflare D1/KV, Supabase, Turso 등): 동시 실행에 더 안전하지만 계정·비밀값이 하나 늘어난다. ② 상태 없이 "24시간 이내"로만 거르기(레거시 방식): 위 ①–③을 해결하지 못한다. ③ Actions 캐시·artifact: 보존이 보장되지 않는다.
- 주의: 같은 workflow가 동시에 두 번 돌면 커밋이 충돌할 수 있다. 그래서 workflow에 `concurrency` 그룹을 지정해 동시 실행을 막는다.
- 관련: FR-DUP-03, FR-MAIL-04, FR-OPS-07, D-09

## D-04 메일 발송 수단
- 상태: 확정 2026-11-11 (사용자 결정 카드 20261111-0100-AN-pm-p1-infra, 추천안 채택)
- 결정: Gmail SMTP와 앱 비밀번호를 그대로 쓴다(레거시 유지). 수신자 주소는 BCC나 개별 발송으로 서로 보이지 않게 한다.
- 근거: 이미 동작하고 비용이 없다. 개인 Gmail의 한도는 하루 500통, 메일 1통당 수신자 500명이라 소수 수신자에게 하루 1통 보내는 데 충분하다(https://support.google.com/mail/answer/22839). 도메인이나 DNS를 설정할 필요가 없다.
- 대안: ① Resend: Free는 하루 100통·월 3,000통이다(https://resend.com/pricing). 발송 API라 SMTP 포트 문제가 없고 전달률이 좋지만, 보내는 도메인을 소유하고 DNS를 인증해야 한다(도메인 인증이 필수인 범위는 미확인). ② Brevo: Free는 하루 300통이다(공식 도움말은 직접 열지 못해 부분 미확인). ③ Gmail API(OAuth): 앱 비밀번호보다 안전하지만 OAuth 동의 화면과 토큰 갱신을 관리해야 한다.
- 위험: 앱 비밀번호는 Google 계정 정책(2단계 인증 해제, 비밀번호 변경) 때문에 무효가 될 수 있다. 무효가 되면 발송 실패 알림(FR-OPS-03)으로 알게 된다. 이때 알림도 같은 Gmail로 나가면 알림까지 실패하므로, 알림은 GitHub Actions의 실패 알림에 맡긴다.
- 관련: FR-MAIL-02, FR-RCP-01~03, FR-OPS-03

## D-05 Claude 호출 구조

  1. **분류·채점** — `claude-haiku-5-5`. 정규화한 항목 전체(제목, 발췌 약 300토큰)를 넣고 항목마다 관련성·유형·중요도·실무 적용성·사건 키(중복 묶음용)를 받는다. 항목이 많으면 50건씩 나눠 호출한다.
  2. **본문 보강** — 코드가 상위 20–30건의 원문 본문을 받아 발췌한다(Claude를 호출하지 않는다).
  3. **편집·신선도 판정** — `claude-sonnet-5-5`. 상위 항목 + 같은 실행의 공식 changelog 요약 + `knowledge/current.md`를 넣고 신선도 등급, 최종 선정(6–12건), 한국어 편집 결과(FR-EDT-03·04 필드)를 받는다.
  4. **권장 사항 메모 갱신** — `claude-sonnet-5-5`. 그날 공식 소스의 변경만 반영한 `current.md` 수정안을 받는다(D-09).
  - 메일 HTML은 코드가 템플릿으로 만든다(Claude가 HTML을 쓰지 않는다).
  - 시스템 프롬프트와 `current.md`는 프롬프트 캐싱 대상으로 둔다.
- 근거: 판단의 질이 가장 중요한 편집·신선도 단계에만 비싼 모델을 쓰고, 양이 많은 1차 분류는 싼 모델에 맡겨 비용을 줄인다. 단계를 나누면 실패한 단계만 다시 돌릴 수 있고, 각 단계의 결과를 로그로 남겨 점검할 수 있다. 레거시는 100건을 한 번에 넣고 자유 텍스트에서 JSON을 잘라 냈는데, 파싱 실패 위험이 있었다(`main.py` 확인).
- 대안: ① 레거시처럼 Sonnet 1회 호출: 단순하지만 입력이 커질수록 비용·품질이 나빠지고 신선도 근거를 넣을 자리가 부족하다. ② 전 단계 Haiku: 가장 싸지만 신선도 판단과 한국어 편집 품질에 위험이 있다. ③ Batch API(50% 할인): 결과가 언제 나올지 보장되지 않아 아침 발송 시각을 맞추기 어렵다. 비용 상한에 걸리기 시작하면 다시 검토한다. ④ Claude 웹 검색 도구로 신선도를 교차 확인: 정확도는 올라가지만 검색 비용과 실행 시간이 늘어난다. 2단계 도입 후보로 둔다.

## D-08 소스 범위
- 상태: 확정 2026-11-11 (사용자 결정 카드 20261111-0100-AN-pm-p1-content, 추천안 채택)
- 결정: 1차는 `docs/소스후보.md`의 A 등급 약 20개로 시작한다. 공식 changelog·릴리스 노트·GitHub releases와 핵심 실무 블로그, HN, GeekNews가 여기에 들어간다. Reddit, X, 일반 매체, arXiv, dev.to는 뺀다. B 등급은 운영 2주 뒤 품질을 보고 추가한다.
- 근거: 이 서비스의 핵심은 "실무에 바로 적용할 기능·사용법"이고, 그 1차 출처는 벤더 changelog다. 레거시는 일반 매체(업계 뉴스)의 비중이 커서 실무 적용성이 낮았다. Reddit은 인증 없는 접근이 403·429로 막혀 있어 클라우드에서 확실하게 동작하지 않는다. X는 API가 유료다(둘 다 2차 출처 보도와 이번 직접 확인 결과). 레거시의 Anthropic RSS 주소는 404로 죽어 있었다.
- 대안: ① 레거시 소스를 유지하고 공식 소스를 추가: 업계 뉴스를 넓게 볼 수 있지만 입력이 늘어 비용이 오르고 실무 밀도가 떨어진다. ② Reddit OAuth 앱 승인을 받아 포함: 실무 후기를 얻을 수 있지만 승인 절차와 정책 변경 위험이 있다.
- 관련: FR-SRC-01~02, `docs/소스후보.md`

## D-09 신선도 판단 방식
